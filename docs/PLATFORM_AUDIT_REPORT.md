# 分子光影查看器：现状审计与平台化发展建议

## 0. 报告目的

本报告回答三个问题：

1. 现有项目已经具备什么，真正的短板在哪里；
2. 如何借鉴 Mol*、NGL、3Dmol.js、ChimeraX 等专业开源/开放项目，而不把本项目变成它们的复制品；
3. 如何把项目稳定地收束为一个面向三种生物尺度、四种工作平台的 **生物 3D 呈现平台**：
   - 细胞；
   - 局部系统；
   - 蛋白质 / 分子复合体。
   - 分子机理。

本报告与 `docs/AI_AUDIT_AND_STABILIZATION.md` 配套。前者负责产品和技术方向，后者负责 AI 修改时的工程约束。

---

## 1. 最终产品定位

### 1.1 正确定位

**分子光影查看器是一个以真实结构数据为基础、针对细胞—局部系统—蛋白质三个尺度，并提供分子机理工作台的实时 3D 呈现平台。**

它不是：

- 试图替代 ChimeraX、PyMOL、VMD 的完整科研分析软件；
- 分子动力学软件；
- 精确的电化学、量子化学或细胞级定量模拟器；
- 单纯播放预渲染视频的播放器；
- 只负责把 PDB 变成漂亮模型的展示网页。

它的优势是：

- 把真实结构放进可理解的生物过程；
- 用结构、配体、构象、区室和粒子流建立因果叙事；
- 允许用户从宏观细胞一路进入局部系统，再进入蛋白质细节；
- 让复杂结构适合教学、演示和交互探索；
- 对“实验结构、坐标推导、模型和教学示意”进行明确区分。

### 1.2 “模拟器”应如何理解

本项目的模拟重点是**机制呈现模拟**，不是追求所有物理量的实验级预测。

可以保留：

- 质子、离子、电子和小分子沿结构路径移动；
- 构象开合、转子旋转、结合/解离和门控；
- Gillespie 或规则状态机驱动的事件；
- 浓度、pH、膜电位和通量的可视化；
- 抗生素、阻断剂、缺氧、解偶联等干预；
- 多个分子机器之间的方向性协作。

但每个过程必须明确：

| 层级 | 含义 | 例子 |
|---|---|---|
| 结构事实 | 来自 PDB、CCD 或数据库 | 配体坐标、辅因子位置、链组成 |
| 坐标推导 | 由结构算法计算 | 孔道、接触、界面、最近路径 |
| 机制模型 | 根据文献和规则推进 | 门控、结合概率、事件顺序 |
| 教学示意 | 为了看懂而放大或加速 | 粒子路径、时间压缩、场景拼接 |

项目可以是专业的，同时承认哪些部分是示意。真正不专业的是把示意包装成精确预测。

## 2. 当前仓库的能力盘点

### 2.1 已有的核心资产

当前仓库不是从零开始，而是已经有一套很完整的呈现能力：

- 单文件 Three.js Web 查看器；
- Electron 桌面版和结构缓存；
- RCSB PDB / ModelServer / GraphQL / CCD 数据链路；
- mmCIF / PDB 解析；
- 生物学组装体展开；
- 团块、结构示意、低分辨率表面；
- 配体球棍、价键、空间填充；
- 结合位点、口袋表面和相互作用；
- 膜、剖切、孔道、标注和讲解卡；
- 构象叠合、Morph、逐链构象变化；
- ATP 合酶、KcsA、核糖体等实时模拟站；
- 呼吸链、光反应、细胞区室和整个细胞；
- 亚基拆装和界面分析；
- `.glow` 场景包和纯数据动画；
- 创意工坊官方/社区索引。

尤其是 `.glow` 场景包已经提供了平台化的重要入口：

- `category` 已区分 `cell`、`system`、`single`；
- 场景是数据，不是任意代码；
- 社区动画通过 `flows`、`reactions`、`pools` 描述；
- 有校验、版本、引用、作者和许可证字段。

这意味着下一阶段不应继续把主要精力放在“再增加一个独立 Demo”，而应把这些能力统一成稳定的平台模型。

### 2.2 现有架构的主要问题

#### A. 单文件已经超过适合持续开发的规模

`web/index.html` 同时承载：

- HTML/CSS；
- RCSB 请求；
- mmCIF/PDB 解析；
- 结构组装；
- 几何算法；
- Three.js 材质和后处理；
- 场景预设；
- 过程动画；
- 细胞模拟；
- UI 事件；
- 工坊格式。

单文件作为“分发产物”是合理的，但作为唯一的“开发源代码”会导致：

- AI 修改时上下文过大；
- 逻辑依赖难以发现；
- 测试难以隔离；
- 一个场景的修复容易影响另一个场景；
- 复制 `skill/assets/viewer.html` 增加漂移风险。

#### B. 三种尺度目前存在，但还是“功能分类”而不是“平台模型”

面板已经有细胞、局部系统、单个蛋白三个选项卡，但它们还不是同一个数据模型的三个视图：

- 细胞场景拥有区室和拥挤，但局部系统/蛋白质进入关系还可以更明确；
- 局部系统主要通过组件拼接表达，缺少统一的系统拓扑；
- 蛋白质场景拥有最丰富的结构功能，但它的选择、表示和模拟状态还没有完全抽象出来。

#### C. 渲染层功能丰富，但缺少平台级预算

当前已有：

- InstancedMesh；
- 自定义材质；
- AO、Bloom、景深、InkPass；
- overlay 场景；
- Worker 口袋表面。

但大型结构的成本仍可能来自：

- 主线程解析和几何生成；
- 低分辨率表面；
- 复杂后处理叠加；
- 每帧标签和 HUD 布局；
- 构象变化时 CPU 更新实例矩阵；
- 场景切换后的资源释放。

下一步需要的是“性能预算 + 自适应降级 + 生命周期”，不是继续增加画质开关。

#### D. 模拟能力很强，但模型层和呈现层还未完全分离

当前过程已经包含真实的状态、速率、计数和干预。但部分过程仍然直接创建或移动 Three.js 对象，导致：

- 难以暂停/重放；
- 难以固定随机种子；
- 难以对模拟结果做单元测试；
- 难以把同一模拟放到细胞、系统和蛋白质三种视图。

#### E. 专业性主要依赖说明和预设，尚未形成统一证据系统

当前很多地方已经认真标记“示意”，例如组件拼接、粒子路径和 ATP/Pi 位置。但随着场景包和社区内容增加，需要把证据等级正式放入数据模型，而不是只依赖说明文字。

## 3. 四个平台设计

## 3.1 细胞层：环境和尺度导航

### 目标

让用户理解：

- 细胞有哪些区室；
- 哪些膜和局部系统位于哪里；
- 分子拥挤、浓度和方向性如何影响过程；
- 从 2 μm 到纳米级结构如何连续缩放。

### 适合保留的功能

- 整个大肠杆菌；
- 细胞膜、外膜、肽聚糖、拟核；
- 细胞质拥挤；
- 背景大分子实例；
- 区室 pH、ATP、NAD(P)H、膜电位；
- 从全景切到细胞一角；
- 核糖体和 KcsA 同时运行。

### 需要补强的专业性

1. **空间语义**：每个局部系统必须有明确的细胞坐标锚点和区室归属；
2. **密度语义**：拥挤度、分子数量、比例和近似方式要可查看；
3. **尺度语义**：镜头显示当前尺度（μm、nm、Å）；
4. **导航语义**：点击一个系统可以进入对应的局部系统场景；
5. **证据语义**：背景复制物必须标记为“按丰度近似布局”，不伪装成原位结构。

细胞层不应强行显示每一个分子的真实原位坐标。它的专业性来自空间尺度、区室关系、数量级和导航的一致性。

## 3.2 局部系统层：协作和通量

### 目标

让用户理解多个分子机器之间：

- 谁接收输入；
- 谁传递电子、质子或代谢物；
- 谁改变膜两侧状态；
- 谁产生 ATP、NADPH 或其它输出；
- 干预一个节点后系统怎样变化。

### 适合保留的功能

- 线粒体呼吸链；
- 叶绿体光反应；
- 细胞一角；
- 细胞色素 c、质体蓝素等移动载体；
- 膜条带；
- 能量转化条；
- 区室浓度和曲线。

### 需要补强的专业性

1. **系统拓扑**：用明确的机器节点、连接边、方向和化学计量表示系统；
2. **空间布局与拓扑分离**：排成一排是视觉布局，不应被误解为实验原位；
3. **过程状态统一**：所有系统都通过统一的 simulation engine 推进；
4. **系统级可观察量**：电子流、质子泵、ATP/NADPH 产量必须来自状态机；
5. **反事实开关**：关灯、缺氧、解偶联剂、抑制剂等必须真正改变系统状态。

局部系统层是本项目区别于普通结构查看器的核心竞争力。

## 3.3 蛋白质层：结构与机制

### 目标

让用户理解：

- 蛋白/复合体由哪些部分组成；
- 哪些残基和配体负责功能；
- 构象变化如何改变状态；
- 结构与过程动画之间有什么对应关系。

### 适合保留的功能

- 任意 PDB；
- 组装体；
- blob/cartoon/surface；
- 配体和 CCD 键级；
- 结合位点和口袋表面；
- 功能核心；
- 孔道；
- 构象 Morph；
- 亚基拆装；
- 残基/部件点选和教学卡。

### 需要补强的专业性

1. **统一选择集**：部件、链、残基、配体附近和界面都使用同一个选择系统；
2. **统一表示组件**：一个选择集可以同时拥有多个表示；
3. **结构来源卡**：实验方法、分辨率、物种、链和引用可查；
4. **坐标推导可解释**：孔道、接触、功能核心显示算法/阈值；
5. **实验态与模型态分开**：不同 PDB 构象、插值构象和教学粒子不能混为一谈。

## 3.4 分子机理平台：一个对象的一条机制链

### 定位

分子机理平台不是第四种尺度，而是建立在蛋白质/小分子结构之上的**过程工作台**。它专门回答：

- 这个小分子如何进入、定位、结合和离开；
- 哪些残基先后发生质子化、去质子化或构象变化；
- 催化反应的底物、过渡步骤和产物如何表达；
- 电子、质子、离子或能量如何经过具体位点；
- 一个蛋白质如何从状态 A 变为状态 B；
- 抑制剂如何阻断某一步。

### 典型场景

- ATP/ADP/Pi 在 ATP 合酶催化口袋中的结合—变构—释放；
- 腺苷酸激酶的底物定位、LID 闭合和磷酰基转移；
- KcsA 过滤器中的 K⁺ 脱水、羰基配位和 knock-on；
- 核糖体解码中心的 tRNA 选择、校对和转位；
- FAD、血红素、铁硫簇或金属中心的电子转移；
- 配体进入口袋、关键氢键网络和水分子替换。

### 设计原则

1. **对象优先**：场景围绕一个小分子、一个活性位点或一个具体蛋白机制，而不是围绕整套系统；
2. **步骤优先**：用步骤条/时间轴表达机制阶段，而不是只播放连续运动；
3. **证据优先**：每一步绑定结构、残基、距离、角度或论文证据；
4. **局部高精度**：关键位点保留全原子/键级表示，远处结构降级；
5. **可干预**：允许替换底物、抑制剂、突变、pH、膜电位或构象；
6. **可重放**：固定 seed、事件日志、单步执行、暂停和回到任意步骤；
7. **可回溯**：从机理步骤进入结构残基、配体和原始数据。

这个平台会把“蛋白质结构查看”和“模拟过程”真正分开：蛋白质平台负责看清对象，分子机理平台负责解释对象怎样工作。

## 4. 开源专业软件的借鉴边界

### 4.1 Mol*

最值得借鉴的是：

- 结构层级数据模型；
- 表示（representation）与数据选择分离；
- 选择集和状态操作；
- 可序列化的状态树；
- 大结构和体数据的分层处理。

本项目不需要复制 Mol* 的完整插件系统，而需要借鉴其基本观念：

> 结构是什么、选中了什么、怎样显示、当前状态是什么，应该是四个可独立理解的对象。

参考：https://github.com/molstar/molstar

### 4.2 NGL

最值得借鉴的是：

- Component / Representation 分离；
- 选择语言；
- 多种表示同时存在；
- 轨迹和构象接口；
- 轻量、可嵌入的 Web API。

本项目已经拥有 blob/cartoon/surface 等多种表示，下一步应把它们统一成 representation，而不是继续增加互相独立的构建函数。

参考：https://github.com/nglviewer/ngl

### 4.3 3Dmol.js

最值得借鉴的是：

- parser、model、viewer、surface worker 的分层；
- `SceneState` 的状态保存思路；
- SurfaceWorker；
- 轻量 WebGL 和导出边界。

本项目的口袋表面已经采用 Worker，应把相同原则扩展到：

- 空间邻域；
- 接触计算；
- 孔道搜索；
- 大型低分辨率表面；
- 结构预处理。

参考：https://github.com/3dmol/3Dmol.js

### 4.4 ChimeraX

最值得借鉴的是专业工作流：

- 命令可重放；
- 模型/选择/会话可保存；
- 分析结果可解释；
- UI 只是命令和状态的一个入口；
- 重计算用 C++/原生层，交互逻辑用上层语言。

本项目不应直接移植 ChimeraX 代码。需要先核查其具体许可证和依赖边界。可以借鉴其工作流思想：

```text
加载结构 → 选择对象 → 设置表示 → 计算结果 → 保存场景状态
```

参考：https://www.cgl.ucsf.edu/chimerax/

## 5. 后续发展建议

### 5.1 第一优先级：把平台基础稳定下来

优先做：

1. 场景 Session 和资源生命周期；
2. 加载取消；
3. 统一结构模型；
4. 统一选择集；
5. 统一模拟接口；
6. FPS/内存/请求/对象数量监控；
7. 固定回归场景。

不优先做：

- 更多新模拟站；
- 更复杂的 Bloom；
- 更高分辨率全局表面；
- 每种蛋白单独定制一套画法。

### 5.2 第二优先级：把三种尺度连起来

设计统一的场景跳转：

```text
cell scene
  └─ local system anchor
       └─ protein machine
            └─ binding site / residue / ligand
```

每次进入下一级时保留：

- 来源场景；
- 目标部件；
- 相机目标；
- 选择集；
- 当前模拟时间；
- 当前干预参数。

返回上一级时恢复状态，而不是重新从头创建一个不相关场景。

### 5.3 第三优先级：把 `.glow` 升级成平台场景格式

当前 `.glow` 已经是正确方向。后续建议增加：

- `evidence`：证据等级；
- `entryPoints`：从细胞/系统跳入蛋白质的位置；
- `observables`：系统可观察量；
- `controls`：模拟参数定义；
- `camera.bookmarks`：镜头书签；
- `selectionSets`：可复用选择集；
- `provenance`：结构和算法来源；
- `compatibility`：最低查看器版本。

社区动画继续保持纯数据，不允许运行任意 JavaScript。

### 5.4 第四优先级：建立“专业呈现”而非“功能堆叠”

专业感主要来自：

- 结构来源清楚；
- 选择和测量可重现；
- 视觉表示有一致规则；
- 结果和参数可保存；
- 模拟可以暂停、重放和复现；
- 大结构稳定；
- 说明不夸大事实。

专业感不是：

- 画面越亮越专业；
- 效果越多越专业；
- 所有结构都必须原子级；
- 每个过程都要显示大量粒子。

## 6. 现阶段结论

项目应该停止向“功能百科”扩张，转向：

> **三层生物尺度 + 一个分子机理工作台 + 一个统一结构模型 + 一个统一模拟接口 + 多种可替换表示 + 可保存的场景状态。**

保留现有功能，收束产品意图：

- 细胞：看环境、区室、拥挤和系统入口；
- 局部系统：看协作、方向、能量和通量；
- 蛋白质：看结构、配体、构象和机制。
- 分子机理：看一个对象在具体步骤中怎样结合、反应、转移、门控或释放。

这个方向既能保留项目现在最有特色的实时机制动画，也能吸收专业结构软件的优点，同时避免把项目变成一个无法维护的通用分子软件。
